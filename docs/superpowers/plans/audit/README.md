# 计划复选框审计（2026-10-29）

> 一句话：**9 份 plan、740 个 checkbox，从「一个都没勾」改成「照着仓库判」** ——
> 565 个勾上，175 个明确写成没做并附理由，**没有一个是为了好看而勾的**。

---

## 0. 为什么做这件事

`docs/superpowers/plans/` 里的 9 份 plan，在本次审计之前：

| 状态 | 份数 | checkbox |
|---|---|---|
| 全空（写完没人回填） | 7 | 543 个空格 |
| 少量勾了一些 | 2 | notification 9 勾 / 110 空；ERP 5 勾 / 67 空 |
| **预勾了 6 个根本没收过的项** | 1 | remote-ssh 的「21 个容器 Up / health-check 通过 / 5 smoke 全绿 …」 |

这三种状态各有各的毛病，但**危害最大的是第三种**：remote-ssh 那 6 个 `- [x]` 把一份
「待执行的验收清单」写成了「已完成的验证结论」——照它读的人会以为那台云 VM 上
21 个容器都起来了，而**那台 VM 上一个容器都没起来过**。

而且空 checkbox 本身就是一句假话：它说「这个没做」，而仓库里绝大部分东西**是做过的**。
照 plan 估完成度，会低估到荒谬的地步（insight 105 个框里 71 个是真做了的）。

所以这次的目标不是「把没做的勾上」，而是**让每个框的状态都能被复核**：
要么有仓库里的证据，要么有一句具体的「没做，原因是 X」。

## 1. 判定口径（本次审计的统一标准）

> 这条标准是**审计结束后才定稿的**。9 份 plan 由 9 个并行审计分别执行，
> 起初各自的口径略有出入（notification 那份接受「markdown 里贴的实测输出」，
> frontend 那份只认「脚本生成的结果文件」）。下面这版是把这两种做法统一后的结果，
> 并已确认**按它重算，9 份 plan 的勾数一个都不变** —— 变的是「凭什么」的说明。

| 级别 | 证据 | 能否单独支撑一个勾 |
|---|---|---|
| **E1 产物级** | 交付物文件 / 类 / 配置 / git 提交在仓库里，且内容与 plan 描述对得上 | ✅ |
| **E2 机器生成级** | 脚本生成并入库的结果文件，如 `tmp_e2e/e2e_report.md`（由 `tmp_e2e/e2e_all.py` 写出） | ✅ |
| **E3 实测留痕级** | markdown 里贴了**原始命令输出**（`BUILD SUCCESS` / `Tests run:` / `Container start: PASS` / `npm run build:prod pass`） | ✅ |
| **E4 文字断言级** | 只有结论、没有原始输出（「跑通了」「已部署」） | ❌ 只作旁证 |
| **E5 外部/运行时** | 容器状态、VM 上的状态、推到外部系统的结果 | ❌ 仓库里没有可复现留痕就不勾 |

**为什么 E4 不算数、E3 算数**：E4 的内容和 E5 一样不可复核 —— 「跑通了」这句话，
谁都能写。E3 里有 `Tests run: 28, Failures: 0` 这种**能被对着原始输出挑错**的东西，
它至少证明「当时跑过」。这条线正好卡在 `docs/verification/**` 上：
**这些文件是证据，不是产物** —— 一份手写的总结只能说明「当时发生过什么」，
不能证明「现在还成立」，所以它对**运行型**步骤只能算 E3，对**交付型**步骤完全不算数。

**三条附则**：

1. **plan 改写了实现，但不等于没做**。代码用另一种同样合理的方式实现了同一目的，
   照样勾，行尾标「（实现方式与 plan 不同：…）」。典型：content 的生成功能做成了
   `script/index.vue` 里的弹窗，没有独立的 `generate.vue` 路由页 —— 功能在，页面形态不同。
2. **口径对不上不是没做，是 plan 写错了**。比如 ERP plan 自查写「spec §1 的 13 条 AC」，
   实际 spec §1 只有 6 条、13 条在 §13 —— 这类框勾上，并在行尾写清「口径本身是错的」。
3. **已勾上的框要重新验，不能默认它对**。本次审计一共推翻了 **6 个**预勾的框
   （全是 remote-ssh 那批虚构的「已验收」）。另外有 **84 个**新勾的框带了一行注记
   （`（部分：…）` 37 个、`（注：…）` 39 个、`（已实现/已核对/已做：…）` 8 个），
   说明「交付物在，但形态/命名/路径跟 plan 写的不一样」—— 这类差异逐条写在行尾，
   也逐条写进了各 plan 的审计报告。

**B3 占大头，这不代表工作没做，只代表「做过」这件事没有留下可复核的痕迹。**
补它很便宜：把命令输出重定向进仓库（或挂 CI）就够了。

## 5. 怎么复核这份审计

```bash
cd /www/Lumen-AI-OPC

# 1) 现在的勾 / 没勾总数（应为 565 / 175 / 740）
for f in docs/superpowers/plans/2026-0*.md docs/superpowers/plans/2026-10-*.md; do
  printf "%-50s %3s 勾 %3s 没勾\n" "$(basename "$f")" \
    "$(grep -c '^\s*- \[x\]' "$f")" "$(grep -c '^\s*- \[ \]' "$f")"
done

# 2) 每个没勾的框都必须带理由（本轮 175 条，一条不漏）
grep -h '^\s*- \[ \]' docs/superpowers/plans/2026-0*.md docs/superpowers/plans/2026-10-*.md \
  | grep -vc '（未完成：'   # 应为 0

# 3) 抽查某一条没勾的理由是否站得住（示例：insight 的 Quartz job）
grep -n 'sys_job_workflow_seed' docs/superpowers/plans/2026-09-08-opc-insight-mvp.md
grep -c 'insight' springboot3/sql/seed/sys_job_workflow_seed.sql   # → 0
```

**审计范围声明**：本次审计只读了仓库与 git 历史 —— **没有起容器、没有连数据库、
没有跑测试、没有改任何业务代码**。唯一被改动的，是 9 份 plan 的 checkbox 状态
和它们顶部的「审计说明」块。plan 的正文散文一个字没动
（`git diff -U0` 可验：改动行要么是 `- [ ]` / `- [x]` 行，要么是新增的审计说明块）。

## 6. 读这批 plan 的人请注意

1. **空 checkbox 不是待办队列。** 那 175 个「没勾」里，127 个是「产物在、缺一次运行留痕」，
   补它们的成本远低于重做。
2. **勾上的也不等于「验收过」。** 565 个勾里绝大多数是「交付物在仓库里」，
   不是「运行结果被验证过」。这两件事在这批 plan 里长期被混着写。
3. **plan 里的数字别直接引用。** 端点数、单测数、工期、类目数 —— 9 份 plan 的
   自述数字几乎全部对不上仓库实测，逐条报告里列了实际值。
4. **要判断「这个功能现在能用吗」，去问 `deploy.sh health`，别问 plan。**
   健康检查是当前唯一被放行的线上验证入口，它查的是**运行中的系统**，
   不是仓库里的历史文档。
